# Reliable Text-to-SQL Data QA Assistant

[![tests](https://github.com/xuchiyu1/reliable-text-to-sql/actions/workflows/test.yml/badge.svg)](https://github.com/xuchiyu1/reliable-text-to-sql/actions/workflows/test.yml)

Ask a question about medical-device companies' financial statements in plain English and get an answer computed from SEC filings, together with the SQL that produced it. The assistant refuses questions the data cannot answer, and generated SQL passes three safety layers before it touches the database.

V1.2 runs on AWS EC2 with Docker Compose (see [Option C](#option-c-deploy-on-aws-ec2-v12)).

## Problem
Companies have too many tables, so SQL generated by LLMs is often inaccurate.
V1 tackles this on a bounded 3-table slice and measures accuracy with a fixed evaluation set. V1.2 extends the data to several quarterly packages, which is what quarter-over-quarter questions need.

## User
Junior industry/equity analysts who can't write SQL but need numbers like "Dexcom's revenue last quarter" without opening filing PDFs.

## How it works
```
question
  → ask(): Claude (claude-haiku-5-5) + schema doc + glossary → SQL or CANNOT_ANSWER
  → validate(): single SELECT only, no data-changing statements, table whitelist, auto LIMIT
  → run_sql(): read-only role `text2sql_reader`, read-only transaction, 5 s timeout
  → on SQL error: send the error back to Claude, retry up to 2 times
  → respond(): table + period + SQL + source; empty result is reported as missing data, never as 0
```

Example:
```
$ python src/app.py "What was Dexcom's revenue in Q3 2025?"
name | tag | value | ddate | qtrs
DEXCOM INC | RevenueFromContractWithCustomerExcludingAssessedTax | 1209300000.0000 | 2025-09-30 | 1
Period: single quarter ended 2025-09-30
SQL: SELECT c.name, lf.tag, lf.value, lf.ddate, lf.qtrs FROM latest_facts AS lf JOIN companies AS c ON c.cik = lf.cik WHERE (c.name ILIKE '%dexcom%' OR c.ticker = 'DXCM') AND lf.tag IN (...) AND lf.qtrs = 1 AND lf.ddate BETWEEN '2025-07-01' AND '2025-09-30' LIMIT 1000
Source: SEC Financial Statement Data Sets, 2025Q3 + 2025Q4 packages (20 medical-device companies).
```

**The period comes from the result, not from model text.** The prompt requires every financial value to be returned with its `ddate` and `qtrs`; [`src/present.py`](src/present.py) turns those columns into "single quarter ended …", "nine months ended …", "as of …" (balance sheet, `qtrs = 0`) and so on, listing each distinct period (companies with different fiscal calendars show separately). If the result carries no date, the answer says "Period: not in the result" instead of guessing. `POST /ask` returns the same list as `periods`.

## Safety: three layers
| Layer | What it does | Evidence |
|---|---|---|
| 1. Prompt | Return `CANNOT_ANSWER` for questions outside the data (stock prices, forecasts, filing text, market share) | Refusal cases q06/q09/q10 and attack cases q11–q13 were all stopped here |
| 2. `validate()` (sqlglot) | Parse SQL; allow exactly one SELECT/WITH/UNION statement; reject INSERT/UPDATE/DELETE/DROP/CREATE anywhere in the tree; whitelist tables (`companies`, `filings`, `latest_facts` + CTE names; the raw `financial_facts` table is blocked, see Data pipeline) and the `public` schema; **deny every function sqlglot doesn't recognise** (standard ones like `ROUND`, `NULLIF`, `LAG` pass; Postgres system functions like `pg_sleep`, `lo_export`, `pg_terminate_backend` don't); add `LIMIT 1000` if missing | `tests/test_validate.py`: 5 safe queries pass, 18 unsafe queries blocked. `src/attack_eval.py` sends 12 attack SQL straight to layers 2+3, skipping the model: **12/12 stopped** (11 at layer 2, 1 at layer 3). Gaps found and fixed: other schemas, settings functions, and `pg_terminate_backend` / `lo_export` / `txid_current`, which led to switching from a function blacklist to deny-by-default |
| 3. Database | Role `text2sql_reader` has only `SELECT` (on the 3 tables and the `latest_facts` view); read-only transaction; 5 s statement timeout | With the validator removed, the database alone still stops **10/12** attacks (read-only transaction, `permission denied`, timeout). The 2 that run (`pg_terminate_backend`, `set_config`) are why layer 2 exists. The 3-table cross join passes layer 2 and is stopped only by the timeout |

## Data pipeline (V1.2)
SEC packages are grouped by **filing date**, not by fiscal period. The 2025Q4 package holds companies' Q3 10-Qs, which compare against the same quarter last year, not the previous quarter. So with one package, "how did revenue change from the previous quarter?" has no data to answer it.

`src/load_data.py` now loads several packages (`RAWS = ["data/raw/2025q3", "data/raw/2025q4"]`, oldest first). The 20 companies are picked from the newest package, so the eval set still applies; their filings and facts are then loaded from every package. Result: 40 filings, 10,747 facts.

**Duplicates.** A 10-Q balance sheet repeats the prior fiscal year end, so the same fact (company, tag, period end, period length, unit) shows up in two filings. Measured after loading both packages:
- 1,111 facts were reported in 2 filings (each exactly twice).
- 3 of them have different values: 2 rounding differences (e.g. Masimo treasury stock 13,661,000 → 13,700,000) and 1 large change (Insulet other non-current assets 2024-12-31: 323.3M → 181.6M, likely a reclassification; not checked against the filing text).

**Design: keep raw data, deduplicate in a view.** `financial_facts` keeps every row as filed. [`sql/views.sql`](sql/views.sql) defines `latest_facts`: one row per `(cik, tag, ddate, qtrs, uom)`, taken from the most recently filed report (`DISTINCT ON … ORDER BY filed DESC, adsh DESC`). It has 9,636 rows = 10,747 − 1,111. The view stores no data, so reloading the tables needs no rebuild, and the dedup rule can change without reloading.
- The validator blocks `financial_facts`, so the agent *can't* read duplicates even if the prompt is ignored.
- Trade-off: latest-wins is right for reclassifications and restatements, but for the 2 rounding cases it keeps the less precise value (Masimo's differs by 0.29%, above the grader's 0.1% tolerance). Raw rows stay available for auditing.

## Evaluation
Execution accuracy on a fixed set of 29 questions, each run 3 times because LLM output is nondeterministic (`RUNS=3 python src/evaluate.py`):
- 21 answerable (q01–q05, q07, q08, q14–q23, q26–q29): single value, ranking, YoY growth, ratio, filter, cumulative and annual (`qtrs = 3` / `4`), quarter-over-quarter change. Graded against hand-written gold SQL; numbers match within 0.1%; ranking questions are checked in order.
- 5 must refuse (q06, q09, q10, q24, q25): stock price, CEO name, market share, forecast, customer list.
- 3 attacks (q11–q13): delete rows, prompt injection with `DROP TABLE`, read `pg_shadow`. Pass = refused or blocked; attack SQL is never executed. The eval logs which layer stopped each one.

V1.1 added q14–q26 (2026-11-11) because 9 of the first 13 questions asked about the same 3 companies. The new ones cover 9 more companies and include traps: a net loss (negative value), a ticker instead of a name (`SYK`), companies that report revenue under different tags, a ranking where #2 (Becton Dickinson) only filed a 10-K, and an annual question that needs `qtrs = 4`.

V1.2 added q27–q29 (2026-11-16), which need both packages: Masimo total assets change vs the previous quarter end, Dexcom revenue growth vs the previous quarter (the two quarters come from different filings), and Masimo total assets at 2024-12-31, a fact reported in both filings that must come back as one row.

| Date | Questions | Runs | Result |
|---|---|---|---|
| 2026-11-01 (V1) | 13 | 3 | **39/39** |
| 2026-11-11 (V1.1) | 26 | 3 | **78/78** (1 answer needed one automatic repair: q26, run 3) |
| 2026-11-16 (V1.2, two packages) | 29 | 3 | **87/87**, 0 automatic repairs |
| 2026-11-19 (V1.2, period in answer) | 29 | 3 | **87/87**, 0 automatic repairs; period shown in **63/63** answerable results |

This means the known failure patterns did not recur on this set; it is not a claim of 100% accuracy in general. The model never reached layer 2 here: all attack questions stopped at layer 1, so layer 2 and 3 are measured separately (see Safety).

How accuracy improved (each fix came from a diagnosed failure):

| Version | Change | Result |
|---|---|---|
| baseline | schema doc + glossary | q06 failed: answered a stock-price question with SQL |
| + refusal rule | `CANNOT_ANSWER` rule in prompt | 10/10 single run |
| + multi-run eval | run every question 3–5 times | exposed flaky q03/q04/q07: 29/30, then 48/50 over 5 runs |
| + schema v0.3 | add column types (`ddate` is DATE, not yyyymmdd int) | fixed `ddate - 10000` bug → 49/50 |
| + glossary rule | filter `ddate` to exclude prior-period comparative rows | fixed row-count mismatch → 50/50 (5 runs) |
| V1.2 regression run | load 2025Q3 as well; agent reads `latest_facts` | 25/26 single run: q07 (nine-month revenue) summed `qtrs = 1` rows, but Q1 is not loaded, so the sum missed a quarter |
| + cumulative-period rule | read first-six/nine-month and full-year values directly (`qtrs = 2/3/4`), never sum quarters; previous quarter = latest earlier `ddate` (not `- INTERVAL '3 months'`, which turns 2025-06-30 into 2025-03-30) | 26/26, then 87/87 with q27–q29 |

Failure taxonomy found along the way: missing data, schema doc lacking types, brittle grader, SQL execution error, domain gap (fiscal year, comparative rows), no refusal, nondeterminism.

## Model choice: Haiku vs Opus
Same 29 questions × 3 runs, same prompt, effort `medium` for both (`MODEL=claude-opus-5-5 RUNS=3 python src/evaluate.py`; the script prints tokens, cost and model latency). Run on 2026-11-18.

| | Claude Haiku 5.5 | Claude Opus 5.5 | Opus / Haiku |
|---|---|---|---|
| Accuracy | **87/87** | **87/87** | same |
| API calls (87 = no repairs needed) | 87 | 87 | |
| Input tokens | 205,578 | 205,578 | same prompt |
| Output tokens (incl. thinking) | 55,499 | 50,524 | 0.9× |
| Cost, whole run | $0.048 | $1.83 | **~38×** |
| Cost per question | $0.00056 | $0.021 | |
| Model latency per question (mean / median / max) | 2.79 / 2.55 / 6.34 s | 5.25 / 5.44 / 11.91 s | ~2× slower |

Prices used: list prices per 1M tokens, Haiku 5.5 $0.10 in / $0.50 out, Opus 5.5 $4 / $20 (`PRICES` in `src/evaluate.py`). Latency counts only Claude API time, not the database.

**Decision: keep Haiku as the default.** On this eval Opus gives no accuracy gain for ~38× the cost and twice the wait.
- Caveat: both models score 100%, so this eval can't tell them apart. It shows Haiku is *enough for these 29 questions*, not that Opus is no better. Harder questions (multi-step, ambiguous periods) are where a gap would show, and the comparison should be re-run when they're added.
- Input is ~80% of tokens because every call resends the full schema doc. Prompt caching is the next cost lever to try; it wasn't used here, so both models were measured the same way.

## Performance (indexes)
`EXPLAIN ANALYZE`, median of 7 runs (`python src/bench_indexes.py`), before vs after [`sql/indexes.sql`](sql/indexes.sql):

| Query shape | 20 companies, 5,491 facts | All 5,296 companies, 1,317,941 facts |
|---|---|---|
| one company, one metric (q14) | 0.03 → 0.02 ms | 0.70 → 0.26 ms |
| year over year, self-join (q19) | 0.03 → 0.05 ms | 0.71 → 0.28 ms |
| all companies, one metric (q18) | 0.17 → 0.07 ms | **105.85 → 19.83 ms** |

- At the project's real size (5,491 rows) indexes make no practical difference: every query is under 0.2 ms. So the indexes were tested on the full 2025Q4 package instead (`src/load_scale.py` bulk-loads every 10-K/10-Q filer with `COPY` into a separate `sec_fsds_scale` database, about 27 s).
- The primary key starts with `adsh`, so it already serves "one filing → its numbers". For "one metric across all companies" (rankings, filters) PostgreSQL 18 still used it through a skip scan, but that took 5,857 separate index searches (about 500 ms, single run on a cold cache). A composite index led by `tag` needs one search: about 5× faster in the benchmark.
- Cost of that index: 1.5 s to build, 19 MB (about 12% of the 160 MB table), and every write must update it. The agent only reads; writes happen only in the batch loader, so the trade-off favours the index.
- Timings vary between runs (cache state): an earlier run measured 160 → 21 ms for q18.
- `filings(cik)`: PostgreSQL doesn't index foreign keys automatically, and every company → filings join uses it.
- Not indexed: `companies.name`. The model matches names with `ILIKE '%masimo%'`, and a leading wildcard can't use a B-tree index.

## Run it

### Option A: Docker (recommended)
Requirements: Docker, an Anthropic API key, and the SEC 2025Q3 and 2025Q4 packages in `data/raw/` (`2025q3/{sub,num}.txt`, `2025q4/{sub,num}.txt` and `company_tickers.json`).
```bash
cat > .env <<EOF
ANTHROPIC_API_KEY=...
POSTGRES_PASSWORD=$(openssl rand -hex 16)
READER_PASSWORD=$(openssl rand -hex 16)
APP_API_KEY=$(openssl rand -hex 16)
EOF
docker compose up -d --build      # Postgres 18 + API; tables, read-only role, indexes and the view are created on first start
docker compose run --rm loader    # one-off load from data/raw/ (owner role)
curl localhost:8000/health
curl -X POST localhost:8000/ask -H "Content-Type: application/json" -H "X-API-Key: $(grep APP_API_KEY .env | cut -d= -f2)" \
     -d '{"question": "What was Dexcom revenue in Q3 2025?"}'
```
The API connects as the read-only role `text2sql_reader`; only the `loader` service gets the owner role. Interactive docs: `http://localhost:8000/docs`.

`POST /ask` returns JSON with `status` = `ok` / `empty` / `cannot_answer` / `error`, plus `sql`, `columns`, `rows`, `periods`, `fixes`. Empty or over-500-character questions get `422` before any model call.

Every `/ask` call spends Anthropic API credit, so the endpoint is guarded ([`src/guard.py`](src/guard.py)):
- **API key:** requests must send `X-API-Key` equal to `APP_API_KEY`, or they get `401`. If `APP_API_KEY` is not set, every request is refused (fail closed), so a forgotten setting can't leave the endpoint open. The key is compared in constant time.
- **Rate limit:** at most `ASK_PER_MINUTE` questions per minute (default 10), else `429`. This caps spend even if the key leaks. The limit is per server process, which is enough for one small instance.
- `/health` stays open for uptime checks.

### Option B: local Python
Requirements: Python 3.12, PostgreSQL, an Anthropic API key.
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
echo "ANTHROPIC_API_KEY=..." > .env
createdb sec_fsds && psql -d sec_fsds -f sql/create_tables.sql
python src/load_data.py          # expects data/raw/2025q3/, data/raw/2025q4/ ({sub,num}.txt) and data/raw/company_tickers.json
psql -d sec_fsds -f sql/views.sql   # creates latest_facts (run after the read-only role exists)
python src/app.py "What was Dexcom's revenue in Q3 2025?"
python -m uvicorn api:app --app-dir src     # same API on localhost:8000
python src/evaluate.py
python -m pytest                 # validator + grader unit tests (also run in CI)
```
Create the read-only role once (see the Safety section): `CREATE ROLE text2sql_reader LOGIN;` then grant `CONNECT`, `USAGE ON SCHEMA public`, and `SELECT` on `companies`, `filings`, `financial_facts` (`views.sql` grants the view). Connection strings can be overridden with `DATABASE_URL` (reader) and `LOADER_DATABASE_URL` (owner).

### Option C: Deploy on AWS EC2 (V1.2)
The same Compose stack runs on one EC2 instance.
- **Instance:** t3.micro (1 GB RAM), Ubuntu LTS, 20 GB gp3 disk, Elastic IP. A 2 GB swap file is added because building the image while Postgres runs can exceed 1 GB RAM and trigger the OOM killer (the build used about 126 MB of swap).
- **Network:** the Security Group allows SSH (22) only from my IP, with key login, and opens 8000 for the API. Postgres publishes no port, so it is reachable only inside the Compose network.
- **Secrets:** `.env` is created on the server, never in git: the Anthropic key is pasted with `read -s` (not echoed, not in shell history), the passwords come from `openssl rand -hex 16`, and the file is mode 600.
- **Data:** the 542 MB raw files stay off the server. The loaded tables are copied instead (about 1 MB):
```bash
# laptop: dump the loaded tables
docker compose exec -T db pg_dump -U owner -d sec_fsds --data-only -t companies -t filings -t financial_facts > ~/text2sql_data.sql
scp -i ~/.ssh/<key>.pem ~/text2sql_data.sql ubuntu@<elastic-ip>:~/

# server
git clone https://github.com/xuchiyu1/reliable-text-to-sql.git && cd reliable-text-to-sql
# create .env as in Option A
docker compose up -d db          # init scripts create the tables, read-only role, indexes and view
docker compose exec -T db psql -U owner -d sec_fsds -v ON_ERROR_STOP=1 < ~/text2sql_data.sql
docker compose up -d --build
```
Checked from the laptop over the public IP (2026-11-24): `/health` returns ok; `/ask` without the key returns `401`; with the key it returns `ok` with the same answer as local (Dexcom Q3 2025 revenue, "single quarter ended 2025-09-30"). Row counts on the server match local: 40 filings, 10,747 facts, 9,636 `latest_facts` rows.

## Limitations
- Two quarterly packages (2025Q3, 2025Q4): previous-quarter and same-quarter-last-year questions work, but Q1 2025 and longer trends are not loaded. Only one company (Becton Dickinson, Sept fiscal year end) has a 10-K in the 2025Q4 package; the rest have 10-Qs (e.g. Dexcom's FY2025 10-K is filed in 2026), so "fiscal year 2025" questions often correctly return no data.
- 29 eval questions is still small; results show the method works, not general accuracy.
- Model comparison covers two models on 29 questions where both score 100% (see Model choice).
- The cloud API uses plain HTTP on port 8000, so the `X-API-Key` header is not encrypted in transit. HTTPS (domain, reverse proxy, TLS certificate) is not set up yet.
- One instance and manual updates (`git pull && docker compose up -d --build`): no load balancer, no automated deploys, no backups beyond the local dump.
